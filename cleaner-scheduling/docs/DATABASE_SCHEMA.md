# PostgreSQL database contract

Migration `0010_default_eligibility` adds `cleaners.eligibility_policy`, constrained to `allowlist` or `all_except_exclusions`. Existing rows retain `allowlist`; new rows default to `all_except_exclusions`. In the default policy, absent eligibility rows allow any active property and explicit `eligible=false` rows exclude it, including after a property is deactivated and reactivated. In legacy mode, only explicit positive rows allow active properties. Existing allowlists are not inferred from current property coverage or silently widened. Downgrade requires a reviewed transition if any default-policy cleaner exists. Stop old application writers before applying the migration; the local launcher backs up state and stops API/web before migrating.

**Current scope (2026-11-09):** automate cleaner scheduling only. Payments, compensation setup and the standalone Settings screen are deferred. Their historical contracts and database records remain for possible restoration; they are not active features. Scheduling policies, hours, consent, eligibility, travel and deadlines remain because they determine feasible schedules.

Proposed logical schema, to be implemented as versioned Alembic migrations. Every table has `id uuid PK` (application-generated UUID), `created_at timestamptz NOT NULL`, `updated_at timestamptz NOT NULL` unless explicitly append-only. All instants UTC; service/availability dates use `date` in America/New_York. Every listed field is NOT NULL unless marked `?`. `FK` uses RESTRICT on deletion unless stated; deactivate operational entities instead of deleting history. `version bigint DEFAULT 1 CHECK(version>0)` applies to all mutable entities; updates use compare-and-swap. JSONB snapshots have application-validated versioned schemas, never arbitrary raw provider payloads.

## Transaction boundaries and concurrency

- Import inbox + acknowledgment persisted first. Reservation upsert, derived tasks, predecessor deadline updates, revision changes, audit and outbox are one processing transaction. Deduplication survives worker retry.
- Publication locks schedule_days for all affected dates (ascending), then task/cleaner rows (sorted UUIDs). Verify input fingerprint and expected revision. Supersede old active assignments before inserting new ones within the same transaction; preserve unchanged versions/acknowledgments. Insert outbox and exceptions before commit. Use retryable serialization/deadlock handling with bounded retry.
- Completion locks task/current assignment, checks actor/version, sets task and assignment completion once, and creates audit/outbox atomically. A historical completion never moves to a different cleaner implicitly.
- Batch preparation locks eligible completed work; global earned_work_key uniqueness rejects concurrent duplicate liabilities even across overlapping periods. Draft void/reprepare must move the existing line transactionally or create a documented replacement while retaining a single payable key. Approved corrections are adjustments, never mutation.
- Approval locks batch and its lines, verifies version/total, freezes contents and records audit. Approval is idempotent; export never changes money state.

## Migration and retention considerations

### M7 implemented additions

Migration `0006_payments` implements `payment_batches` and `payment_line_items` and adds PostgreSQL `btree_gist` rate-period exclusions (default and property scopes separately). Installation requires the migration role to have permission to install the trusted extension. Existing conflicting rate rows make migration fail for review; no historical migrations are edited or rate data silently rewritten.

Batch extensions: `exclusions jsonb NOT NULL` (task/reason list), `frozen_lines jsonb NULL` (set on approval/void). Line extensions: `cleaner_name text NOT NULL`, `property_alias text NOT NULL` are export snapshots. Cleaning `earned_work_key` is `cleaning:<task UUID>`; corrections use `adjustment:<global correction key>`. A second partial unique index on cleaning task ID guards even alternate earned-key formatting. `payment_batches.idempotency_key` stores a digest of actor/request key rather than the raw header. Updates to approved/void batches are rejected by trigger. Line content is immutable: only its `batch_id`/`updated_at` may change when moving from a void batch into a draft. Hard deletion is denied. Frozen old batch contents preserve prior membership.

Rate contents cannot be changed/deleted; an audited future replacement may narrow only the old rate's upper date bound where no published assignment is affected. Financial actions use a business-wide transaction advisory lock (appropriate to the single-business scale) before resolving request idempotency, plus database uniqueness. Approval rechecks completion/disputes, line sums and every cleaner subtotal; export uses frozen snapshots in deterministic order. These implementation extensions refine the logical schema above.

Use `timestamptz`, not timestamp-without-zone, for instants; translate date-only source data only through approved policy. Introduce constraints after backfill validation, use concurrent indexes outside transaction where necessary, and review migration locks on realistic data. CI upgrades an empty DB and a prior released schema; test backup restoration before destructive changes. Use soft deactivation and restrictive FKs to preserve financial/audit history. Proposed retention is in [security](SECURITY.md); purge encrypted webhook/SMS/location payloads separately from minimum audit/financial records. Preserve hashes/keys needed for deduplication after payload purges.

2026-11-07 deadline-rule transition: retain nullable `deadline_at` and `pending_deadline` for historical compatibility; do not edit applied migrations. New/recomputed tasks persist the earlier of checkout + 48 elapsed hours and buffered next check-in. Dashboard and solver cap legacy null/later values immediately. Earlier `manager_target_at` tightens that bound. Review incompatible published/locked assignments before shared rollout; no silent unlock or completion/payment history deletion is permitted.

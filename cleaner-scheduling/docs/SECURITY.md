# Security and operational controls

Scope: one business, operator dashboard and cleaner SMS. Main threats are unauthorized schedule/payment changes, forged provider commands, sensitive property access disclosure, leaked contractor data, replayed events, and accidental production sends. These controls implement FR-24/FR-26/FR-27; do not claim legal compliance without the appropriate business review.

## Authentication and authorization

Use managed OIDC authentication with backend verification of issuer, audience, signature, expiry and key rotation; short-lived tokens and MFA for owners/managers are required before launch. No self-assigned roles from browser claims. Resolve roles from backend-managed operator records. Viewer: operational read with masked personal data and no rates/payments; manager: property/cleaner/schedule/exception operations, completion and payment preparation/approval; owner: all manager permissions plus users, compensation rules and production policy/config approvals. Scheduler identity: narrowly scoped preview/publication only, not rates/payments. Twilio ingress authenticates provider signature and binds sender to cleaner; it does not create a manager principal.

Enforce role checks in every API/service write and sensitive read. Prevent IDOR even within this single-business app: cleaner links can read only that cleaner's current assigned job and sanitized instructions. Expired/revoked links fail closed. Use CSRF protection for cookie-based sessions; restrict CORS to deployed UI origins and secure HttpOnly/SameSite cookies where used. Backend JWT authorization remains mandatory. Deactivated operators lose access without waiting for a UI refresh.

## Secrets and environment separation

Use managed secrets storage and workload identities. Do not place tokens in browser bundles, URLs, screenshots, logs, Git history, CSV, fixtures or `.env.example`. Separate production/staging accounts, databases, queues, auth audiences and callback URLs. Local `.env` stays ignored. Rotate keys on suspected exposure and revoke compromised credentials; scan commits and CI output. Production flags must fail closed, with mock integrations as defaults. Production startup rejects mock auth, unapproved policies and missing security configuration. Enabling provider ingestion alone cannot enable SMS dispatch.

## Webhook authenticity, replay and ingress

Validate raw request bytes and documented signatures using current official SDKs where supported. Use the externally visible callback URL safely behind a trusted proxy; do not trust arbitrary forwarded-host headers. Reject invalid signatures before processing. Enforce provider replay windows when documented and event uniqueness always. Quarantine unknown message identities/statuses. Hospitable webhook validation details remain unverified: keep production ingress disabled pending documented validation or an approved authenticated re-fetch alternative. Provider absence of a documented signature never justifies accepting arbitrary POSTs. Persist inbox before acknowledging, and constrain body size and request rates.

## SMS consent and sensitive data

Manager must verify US messaging registration/brand/campaign or other appropriate sender requirements, opt-in evidence, opt-out behavior, HELP response, allowed messaging hours and carrier rules before launch. Obtain independent compliance advice as needed; this specification does not assert a particular campaign classification. STOP immediately suppresses queued application sends and persists opt-out; do not override it with scheduling policy. Use approved provider-managed opt-out behavior without duplicate application replies. Contact failures appear through an independent operator channel.

Property addresses and entry/access instructions are sensitive. Encrypt instructions and phone/location payloads at rest with managed keys, restrict views and audit access. Never include entry codes in assignment SMS; use revocable scoped detail links or manager-mediated delivery. Cleaner links use high-entropy opaque tokens, store only token hashes, expire/revoke on supersession/unavailability, and are excluded from analytics/logging. Do not collect guest personal information for cleaning coordination. Limit daily location collection to operational start locations; no continuous tracking. Mask phone numbers in general views and exports.

## Audit, logs and retention

Append-only audit records contain actor, action, entity, UTC time, request/correlation ID, reason and redacted changes; DB role cannot update/delete audits. Log IDs and error codes instead of message bodies, credentials, raw provider payloads or access secrets. Access to audit search/export is restricted and logged. Proposed retention requiring manager/accounting review: raw webhook bodies 7 days, SMS bodies 90 days, daily precise starting locations 30 days, operational histories/audits 1 year, payment/rate history 7 years. Preserve deduplication keys/hashes without sensitive payloads for business replay safety. Implement configurable purges and legal-hold exceptions; do not purge financial linkage required to prevent duplicate liability.

## Transport, storage and backups

TLS for browser/API/provider callbacks and database connections; private network DB/Redis; encrypted managed storage/backups. Least-privilege API/worker/migration/read-only roles and separate encryption key permissions. Daily encrypted backups plus provider point-in-time recovery where available. Proposed RPO ≤24 hours/RTO ≤4 hours require manager approval and a timed restore drill before launch. Restore in isolation with production dispatch disabled; validate reservation cursor, assignment versions, compensation and outbox deduplication before reconciling external effects. Restoring a DB must never blindly replay SMS already accepted by the provider.

## Abuse prevention and secure deployment

Proposed rate limits: authenticated reads 120/minute/operator, writes 30/minute/operator, solver previews 5/minute/operator and one active solve/date; webhooks 600/minute/provider with burst queueing and verification. Tune against verified provider retries and pilot load; do not drop legitimate events silently. Bound solver CPU/memory/time, CSV uploads (5 MB/10,000 rows), webhook bodies (256 KB), pagination and date ranges. Prevent SSRF in feed URLs/geocoding inputs: allowlist approved HTTPS hosts, reject private/loopback destinations and validate redirects/DNS rebinding. Escape UI text; sanitize CSV formula-leading cells. Use parameterized SQL and safe serialization.

Pin dependencies and lockfiles, run secret/dependency checks, review network egress, build immutable artifacts, use non-root workloads and restrictive security headers/CSP. Separate readiness/liveness, apply migrations once, monitor failures and test rollback. CI never has production SMS credentials; integration tests use sandbox/mocks. Owner approval to activate dispatch is recorded, requires all launch gates, and has an immediate kill switch that suppresses pending sends without deleting business state.

## Local cleaner setup

Local cleaner setup (2026-11-10): new protected fields use AES-256-GCM with random 96-bit nonces, an authenticated format prefix and an HKDF-SHA256 derived encryption key through pinned `cryptography==50.0.2`. The existing development envelope remains readable for old synthetic data; new writes never use it. The real-data workspace requires a separate owner-only `FIELD_ENCRYPTION_KEY_FILE`, never the application signing secret. The validated key is cached for the process, and launcher fingerprint checks reject a changed or missing key after initialization. No silent regeneration or key rotation is performed for existing encrypted data.

The launcher saves a matching private `.field-key` copy beside each pre-migration database dump. Preserve the key and matching database backup outside Git; encrypted fields cannot be recovered from the database alone. These local backups do not establish production RPO/RTO or an off-device restore guarantee. Do not roll back to code that cannot read the new ciphertext envelope after saving real cleaner data.

Phone lookup HMACs and sensitive setup idempotency digests use the local field secret. Phone numbers are never returned in cleaner lists or audits; starting addresses are returned only through the manager-authorized weekly-hours endpoint. The frontend receives only its separate application session token, not provider or data-encryption keys. Address saves in this workspace cannot invoke the demo geocoder/router. No cleaner data is sent to Hospitable or a routing provider. Local setup mutations remain authenticated, rate-limited, audited, idempotent or version-checked, and serialized with source application. SMS, cleaner links, provider callbacks, schedule preview/publication and policy changes remain blocked.

## Incident handling

On suspected exposure/forgery: disable dispatch/affected ingress, preserve audit evidence, rotate credentials, assess impacted instructions/contractors, notify manager through independent channel, reconcile bookings and schedule state before resuming. On provider outage: mark health stale, retain durable work, escalate and follow freshness gates. On opt-out failure: suppress all sends to affected number and investigate queued intents/callbacks. Record incident timeline and validated recovery; never report recovery from a green process health check alone.

Cleaner onboarding grants are purpose-separated from existing job links. They authorize only the named active cleaner’s recurring hours/breaks/starting address, with bounded expiry, replacement/removal revocation, server-bound identity, rate limits, keyed idempotency digests, encrypted addresses and cleaner-attributed audit. Tokens travel in URL fragments and authorization headers, never query/path parameters or audit/log bodies; only hashes are persisted. The cleaner proxy ignores operator cookies for this route and enforces same-origin writes. The onboarding page has no manager navigation, sends no referrer and forbids framing. Local-only origin/host restrictions remain; public onboarding requires a separate reviewed HTTPS deployment that does not expose local owner-session bootstrapping.

Free routing extension (2026-11-11): explicit LOCAL_FREE_ROUTING opt-in is accepted only in the isolated read-only Hospitable workspace. Verified source coordinates are encrypted locally, with plaintext coordinate columns left empty. The private OSRM container publishes no host ports and logs warnings only, preventing route URLs/coordinates in request logs. Only a cleaner’s submitted starting address goes to the fixed official Census geocoder; no credentials, guests, access codes or house addresses are sent. Requests have bounded timeouts/retries/size limits and no synthetic fallback. Cleaner identity and protected setup authorization remain unchanged. Captures bind graph/property identity, check road proximity and preserve null legs; background writeback uses active-cleaner, encrypted-address and version checks under the publication lock. Graph preparation pins software, records source hashes and retains prior generations; no billable routing account is configured.

Automatic email delivery (2026-11-12): separate local_email_automation_enabled authorization is required in the isolated workspace with approved scheduling policy,current read-only source data,local routing and Gmail configuration. Email recipients/content are encrypted locally; audit/log entries contain IDs/status/counts only. Delivery state is reserved beforeSMTP; uncertaintynever permits an automatic resend. The email application role has noDELETE privilege on its ledger. Applied migrations and backup/encryption keys are preserved. Hospitable adapter remains GET-only and SMS dispatch remains blocked.

Cleaner portal/hosting boundary (2026-11-12): jobs-purpose grants use a portal-specific HMAC and storedhash,7-day expiry,active-cleaner checks and revocation; onboarding tokens cannot act as jobs tokens. Changing a cleaner email revokes existing job grants. Tokens remain URL fragments and Bearer headers,never query/path logs or localStorage. Public APIs ignore owner session cookies. Page/API no-store/referrer protections and frame blocking apply. The prepared pinned Caddy2.11.9 gateway exposes only cleaner/onboarding pages,exact APIs and static assets; manager pages,/session and generic APIs remain private. Backend still only trusts internal/localhosts. No gateway was started publicly; manager access remains loopback/SSH on a future single-owner host.


## Hosted hardening implementation (2026-11-14)

The owner requested stronger protection for customer data and chose to retain the Railway address. This is layered application and Railway edge hardening, not a claim that compromise is impossible or that an independent penetration test has passed. Existing workspace row security, authenticated manager sessions, scoped cleaner grants, encrypted private fields, idempotent writes, private backing services and default-off customer gates remain in force.

Railway domain inventory on this date showed only the web service publicly routed; API, PostgreSQL, Redis and routing had no public domains. The native Railway edge API accepted the two rules in `infra/railway/edge-rules.json`: block secret-file/unrelated server probes and bypass application edge caching. Existing edge rules were empty before applying these. These narrow rules are not a complete managed attack-signature ruleset. Under Attack Mode is available but remains off during ordinary operation because it challenges browsers and can reject non-browser clients. Emergency operation is `railway waf under-attack enable --service web --duration 1h`; disable with `railway waf under-attack disable --service web`. To roll back custom rules, restore the prior empty ruleset through the same edge API. Railway validates the complete ruleset before changing it. Official evidence: https://docs.railway.com/networking/edge-rules and https://docs.railway.com/networking/public-networking/specs-and-limits.

The web boundary enforces actual streamed byte limits of 32 KiB for account/session submissions and 6 MiB for API requests, with a ten-second body-read deadline. The private API independently enforces 6 MiB and ten seconds before parsing. Oversized, malformed-length and slow requests receive sanitized errors; rejections log only code/status/request ID. Uvicorn caps concurrent requests at 64 and keep-alive at five seconds. Backend rate increments and expiry are atomic in Redis.

The web service signs Railway's documented `X-Real-IP` with a dedicated private `WEB_PROXY_SECRET`, binding method, path and a timestamp; the API validates the signature, IP and sixty-second age before using that identity in rate limits. Client-supplied forwarding headers are not trusted directly. Trusted private calls without this metadata retain their peer identity. The matching secret was staged privately on API and web without triggering deployment and must never be configured as a public browser variable.

Every app page receives nonce-based script CSP with no production unsafe-eval, frame denial, nosniff, no-referrer and a restrictive browser permissions policy. Inline styles remain permitted for the existing UI. Production HTTPS responses enable HSTS. Rendered nonce behavior and real sign-in still require live verification after deployment. Sensitive responses are no-store; public generic proxy access to backend health endpoints is blocked. Protected API schema/docs are disabled.

The web image serves as the existing node user with its Next cache writable. API startup briefly provisions the private volume as root, then drops supplementary groups and switches to UID/GID 10001 before loading settings, running migrations and serving requests. After the bounded migration subprocess finishes, its administrative database password is removed from both the settings object and runtime environment, and startup replaces itself with a fresh unprivileged serving process using only the sanitized environment. Process replacement also removes the original secret-bearing environment memory; merely updating Python’s environment mapping would leave original bytes visible through procfs. The API's database sessions retain the existing restricted application role. Startup reclaims the private directory before file preparation, so subsequent restarts retain strict key ownership validation.

Rollback to a pre-hardening root-serving API image requires an operator to restore `/data/private`, `/data/private/field-key`, `/data/private/gmail.json` and `/data/private/manifest.json` ownership to UID/GID 0 before that older startup reads its key. Preserve directory mode 0700 and file mode 0600. No schema migration or business-data change accompanies this hardening. Keep paired database/key backups; ownership rollback does not replace key recovery. The new proxy secret can remain configured when rolling back older code, which ignores it.

Runtime npm and Python advisory scans reported no known vulnerabilities on this date; this does not cover unknown vulnerabilities or every operating-system library. CI adds runtime dependency audit gates, with the auditor pinned to pip-audit 2.10.1, and Dependabot proposes weekly uv, npm and GitHub Actions updates through PRs. GitHub workflow permissions are read-only. No test or fixture files were added or changed under the owner's explicit prohibition. Existing suites, type checks, lint and builds remain required gates; the new controls do not yet have dedicated regression tests.

Remaining launch work includes manager MFA/account recovery, verification of administrator MFA on Railway/GitHub/email, external alert routing, a timed isolated restore drill, and independent penetration testing. Do not represent these as completed by a firewall or clean dependency scan.


## Manager MFA preparation (2026-11-14)

Opt-in authenticator setup is implemented through the authenticated account resource: GET `/v1/accounts/me` returns only MFA status/count metadata, PATCH on the same path requires password reauthentication and an idempotency key for begin/confirm/disable actions. Pending setup expires after ten minutes and is bound to the initiating session; activation requires a working six-digit code. Seeds and sensitive retry responses use the existing authenticated field encryption, and secrets never enter logs or browser storage. Standard RFC 6238 SHA-1/30-second/six-digit codes accept at most one time step of clock drift and reject reused counters. Eight random 128-bit recovery codes are stored only as account-bound hashes and consumed transactionally. Account locks serialize enrollment, factor consumption and session creation. Activation/disable revokes sibling sessions while preserving the initiating password-and-code-verified session. Password-only signup/login retries cannot bypass subsequently enabled MFA.

Migration `0024_manager_mfa` adds only nullable/defaulted account columns and grants update access only to those columns. Its downgrade refuses while any account has active MFA. Enrollment does not happen automatically. Initial CI reported two failures because existing readiness assertions expected revision 0023. The owner explicitly authorized updating only those two existing revision expectations to 0024; no other tests or fixtures were changed and no dedicated MFA test cases were created. All existing gates must pass before rollout.

Official protocol evidence reviewed: https://www.rfc-editor.org/rfc/rfc6238 and https://pages.nist.gov/800-63-4/sp800-63b.html. This implementation is not an assertion of NIST certification or phishing resistance; authenticator OTPs can still be phished.

## Application security alert delivery (2026-11-14)

A separate default-off `SECURITY_ALERT_EMAIL_ENABLED` flag and private `SECURITY_ALERT_EMAIL` recipient prepare account security alerts through the existing generic outbox and Gmail sender. Five failed password attempts against a known account within a fifteen-minute counter window queue an encrypted notice; unknown accounts only produce redacted logs. Queue commits precede the invalid-login response. The existing workspace outbox constraint deduplicates each account/event kind per UTC hour, including concurrent requests. No new schema or dependency is introduced.

The independent worker drains all workspaces, including managers who have not connected Hospitable, and does not depend on cleaner dispatch flags. Definite pre-send connection failures receive at most three bounded attempts with backoff. The worker commits a sending state before message transmission. Expired sending leases and unknown SMTP outcomes become terminal uncertain records rather than automatic resends. Accepted means SMTP acceptance, not inbox delivery. Logs retain only IDs, event kinds and delivery/error codes. No sample or artificial attack emails are sent by preparation.

The selected recipient is configured privately; it is not stored in source. Railway account notification preferences already showed email-and-in-app delivery for deployment failure, crashes/OOM, usage and restricted-service events. That native screen uses the Railway account email and did not offer a separate address. Application notices and native outage notices therefore have distinct routing; forwarding native notices to the selected business mailbox still requires a verified mail route or a supported platform contact setting. No account email or access permissions were changed.


MFA activation, disabling and successful recovery-code login queue security notices in the same transaction as the account change. Invalid MFA codes join the failed-login counter. Exact idempotent retries do not consume another recovery code or create duplicate notices. The owner explicitly authorized only the two existing readiness revision-assertion updates needed for migration 0024.

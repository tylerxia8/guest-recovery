## Webhooks, reconciliation and failure semantics

The proposed application ingress is `POST /v1/webhooks/hospitable` (not an upstream endpoint). Disable it until webhook capability and validation are verified. Preserve raw bytes for signature checking in memory; validate using documented algorithm and canonical public URL. Enforce documented replay protection where possible plus durable event deduplication. If signatures are unsupported, keep ingress disabled until an approved alternative authenticated verification/re-fetch strategy exists. Do not invent an HMAC scheme for Hospitable.

Persist an inbox record before 202. Dedup by documented event ID; if unavailable use a documented stable composite/canonical digest and reconcile authoritative state. Out-of-order source revisions cannot replace newer reservations. If no reliable ordering exists, fetch authoritative current state where supported; quarantine ambiguous updates if freshness cannot be established. Worker transaction updates reservation, affected departure and predecessor tasks, audit and outbox; source cursor commits only after all page effects persist.

Proposed incremental reconciliation every 15 minutes and full comparison daily, subject to provider limits. Paginate fully and mark snapshot completeness explicitly. Only documented authoritative complete snapshots may infer deletions; otherwise require explicit cancellation or manager-reviewed reconciliation. Webhooks accelerate updates but never replace reconciliation. Failed pages do not advance cursor; retry with jitter, respect retry hints, alert after bounded failure. Outage marks sync stale, retains last-good state, queues re-sync, and blocks affected publication beyond freshness threshold. Recovery replays deduplicated events, completes full reconciliation, detects changes since last good state, and regenerates impacted previews before resuming dispatch.

## Authorized fallback modes

1. Authorized calendar feed: fetch a manager-approved secret feed URL server-side; treat it as a secret, allowlist hosts, prevent SSRF. Map stable event IDs to properties; validate update/cancellation semantics against the feed format. Feeds may lag and omit cancellation, exact times or instructions. Never promise real-time operation. Record last successful refresh and source age; request manual confirmation of urgent bookings.
2. Authorized structured import: manager uploads UTF-8 CSV with `provider,external_id,property_external_id,status,checkin_at,checkout_at,source_revision,source_updated_at`. Times must include offsets; optional revision/time require a manager-confirmed ordered snapshot if source ordering is unavailable. Validate to a dry-run report before commit, reject duplicate conflicting IDs, and store upload digest/idempotency key. No spreadsheet formulas are executed. Proposed max 5 MB/10,000 rows.

Fallback sources are explicit operating modes, not simultaneous competing authorities for the same booking. Switching requires manager approval, mapping review and reconciliation to avoid duplicate tasks. Inferred date-only times require approved policy and provenance. Fallback launch requires recorded acceptance of source latency, missing fields, manual checks and readiness risks. Mock development is unblocked regardless of account API eligibility.

## Guest departure message reads (2026-11-15)

The official [OpenAPI export](https://stoplight.io/api/v1/projects/hospitable-eng/public-api-docs/nodes/V2/public.json?fromExportButton=true) and [Message schema](https://stoplight.io/api/v1/projects/hospitable-eng/public-api-docs/nodes/Message.json), retrieved 2026-11-15, document GET `/reservations/{uuid}/messages`, the `message:read` scope, and a limit of two requests per minute per reservation per OAuth client or PAT account. The response documents a `data` array without pagination parameters or metadata. The reader therefore makes one bounded collection read rather than inventing pagination. Its existing response-byte and overall time limits remain enforced; reads and retries for the same reservation in one client are spaced at least 31 seconds apart. The worker must also serialize polling across client instances.

`Message` documents `platform_id`, `reservation_id`, `sender_type` (`host` or `guest`), `content_type`, `body`, `created_at`, and `source`. It documents no generic message UUID or sent/delivery-status field. Guest departure candidates require an exact reservation match, `sender_type=guest`, `source=platform`, `content_type=text/plain`, a bounded string platform identity and body, and an offset-aware `created_at`; timestamps normalize to UTC. Unknown senders, malformed guest records, duplicate identities and ambiguous timestamps fail the read. Host messages, unmatched conversations and nonplatform/nontext records cannot release cleaning. Raw message bodies are transient input and must never be logged or retained as source payloads.

No message text or reservation identifiers were printed or retained. This verifies that token’s current read entitlement, not every future customer account. A permission failure retains the checkout fallback and never implies departure. This adds only GET access, without webhooks, message sends or changes to Hospitable.
